# 速度計測フィクスチャー（開発専用）

初回のファイル登録で、サムネ生成だけの状態とフルサポート（ID解決・dHash＋類似照合・マーカー確認が並走する）の状態で
処理時間にどれだけ差が出るかを、実ファイルで測るための仕組み。リリースビルドでも使える。UIの文言は日本語直書き（i18n 対象外）。

## 有効化

設定→デバッグの4つ目のチェックボックス「サムネ周りのリファクタリング用ログ（計測フィクスチャー）」。
state キーは `app_log_thumb_refactor`（既定 false）。ONの間だけ、ファイルカードの右クリックにメニューが出る
（実フォルダ表示中のみ。お気に入り・検索・類似の表示中は出ない）。

## メニュー

| 項目 | 内容 |
|---|---|
| …クリアし計測を開始する（サムネのみ） | サムネ生成だけを走らせる。ID解決・dHash・マーカー確認は起動を抑止する |
| …クリアし計測を開始する（フルサポート） | 全段を通常どおり走らせる |
| DB消去前に戻す | 最初のクリア前に退避したDBへ戻す（再起動で適用）。退避が無い間は無効 |

## クリアの範囲

表示中フォルダ**直下**のファイルだけ（サブフォルダは対象外）。

- ID層（`delete_id`）。評価・しおり・お気に入り・重複マーカー・dHash・消した組も連動して消える。未解決リストの行も消す
- cache.redb のサムネ（JPEG・生成元・サイズ・フィルタ・状態）

実行前に確認ダイアログを出し、spread DB 全体を `perf_fixture/before.redb`（設定フォルダ直下）へ退避する。

## 退避と復元

- 退避は**復元するまで初回のみ保持**する。「サムネのみ→フル」と続けて測っても、最初のクリア前に戻れる
- 復元は再起動で適用する（起動中のDBは差し替えない）。適用時は、現DBを `perf_fixture/after-measure.redb` へ退避し、
  `before.redb` を消す（次のクリアで改めて取る）
- 戻るのは spread DB 丸ごと。計測後に他フォルダで行った評価の変更も、退避時点に戻る
- cache.redb は対象外（作り直せるため）

## 計測と出力

標準出力へ `println!`（デバッグログ設定とは無関係）。フルサポートは次の4段がすべて完了した時点、
サムネのみはサムネ生成の完了時点で、集計を1回出して計測を終える。

| 段 | 完了の判定 | 1件の処理時間 |
|---|---|---|
| ID解決(FP) | ワーカーの `Done` を受けた時 | `resolve_file` 1回 |
| サムネ生成 | 保留が空かつ待ちキューが空になった時 | `generate_thumb` 1回（生成レーンのスレッド） |
| dHash+類似照合 | サムネ完了**後**に出した依頼の `Final` を受けた時 | サムネ読み出し＋dHash 1件。DB操作（索引引き・書き込み）は「DB待ち」に別計上 |
| マーカー確認 | 遡及検出の `Detected` を受けた時 | `detect_in_dir` 1回 |

出力項目: 総時間（必要な段の完了時刻の最大値）、段ごとの開始・終了（計測開始からの相対秒）・件数・累計処理時間・
平均 ms/件・DB待ち。累計処理時間が壁時計の所要時間のスレッド数倍に近ければ並列で回っており、所要時間より小さければ
待ち（I/O・ロック・他段との競合）が大きい。

注意: フォルダを開いた直後（約0.9秒）と入力操作の直後は、サムネの並列度が絞られる（`thumbnail_local_limit`）。
計測中は操作しない。

## 全件サムネ生成と内訳

- 通常のサムネ生成は遅延式（表示範囲＋スクロール方向に1画面分だけ）で、画面外は生成されない。dHashもサムネができた分だけ。
  一方ID解決は一覧の全件を先頭から処理するので、段ごとの件数が揃わない
- 確認ダイアログのチェック「画面外も含めて全件のサムネを生成して測る」（既定ON）がONの間、計測中は一覧の全ファイルを
  毎フレーム先読みキューへ積む（ID解決待ちのファイルは解決後に積む）。サムネ段の完了は、全件を積み終えてキューと保留が空になった時
- ID解決の内訳（段の行の下に `└` で出す）: `metadata(stat)`、`DB参照(quick_hit)`、`観測(observe)全体`（FP各行を含む）、
  `FP: open+stat`、`FP: 窓の読み(seek+read)`、`FP: SHA-256`、`DB解決(resolve_path)`。`観測全体` と `FP:` 各行は重複して数えている
- ファイルキャッシュの影響: 2回目以降はOSのキャッシュが温まる。比較するときは、順序を入れ替えて繰り返すか、
  キャッシュを落とした直後（`sync; echo 3 > /proc/sys/vm/drop_caches`、root）の値を使う

## 検証済みの結論（FP読みの先読みは効かなかった）

ID解決のFP読み（ファイル1つにつき5か所のシーク）を複数スレッドで先読みする試作（`NEKO_FP_THREADS`）を作り、
外付けHDDのコールドキャッシュで測ったが、ほとんど効かなかったため巻き戻した。

| 先読み本数 | 総時間 | ID解決の壁時計 | FP窓読みの1件あたり | 実効（÷本数） |
|---|---|---|---|---|
| 1 | 12.56s | 12.27s | 72.0ms | 72.0ms/件 |
| 2 | 11.79s | 11.51s | 136.4ms | 68.2ms/件 |
| 3 | 11.62s | 11.32s | 200.3ms | 66.8ms/件 |
| 4 | 11.21s | 10.88s | 258.2ms | 64.5ms/件 |

- 同人誌50（168件）。ディスクがシークで飽和しており、本数に比例して1件あたりの待ちが伸び、実効のスループットは動かない
- 支配項はFPの5か所のシーク（約13ms×5）。SHA-256・DB・dHash・マーカーはコールドでも誤差
- FPの窓を減らす案は、FP仕様の変更になり既存のID照合が全無効になるため採らない
- SSD上では未計測。効果があるかは分からない。再試作するなら、SSDの計測を先に取る
- 代わりに、FP読みのコストを「ユーザー操作の邪魔にならない時間」へ動かす方針（表示範囲の優先、手すき生成）を取る

## 実装

- `src/perf_fixture.rs` — セッション（モード・段ごとの記録・集計文面）。ワーカーからは `item` / `lock_wait` / `stage_done`
- `src/perf_fixture_db.rs` — 退避・復元予約・起動時適用、フォルダ直下のID層クリア
- `src/view_explorer/perf_fixture_ui.rs` — カードのメニューと確認ダイアログ
- サムネのみの抑止: `start_identity_resolution` / `request_marker_probe` / `request_marker_detect` / `request_thumb_hash` が
  `perf_fixture::is_thumb_only()` で戻る

## 既知の限界

- 「サムネのみ」でも、ID解決が走らないので、サムネ生成が「検証中」で待たされない分だけ通常より速い可能性がある（それが比較したい差）
- 遡及検出は `marker_view_active()` の時だけ走る。走らない画面状態では「マーカー確認」が完了せず、集計が出ない
- 起動時のバックフィル・自動掃除（ID層の別ワーカー）は計測に含めていない

## 手動確認項目

1. ゲートOFFではメニューが出ない／ONで出る。設定を再起動後も保持
2. サムネのみ: クリア→サムネ生成→集計が1回出る（サムネの段のみ）。ID解決が走らず、ファイルに「検証中」が出ない
3. フルサポート: 4段すべての行が出て、総時間が出る
4. 続けて両方測った後、「DB消去前に戻す」→再起動で、最初のクリア前の評価・しおり等が戻る
5. 退避に失敗する状況（設定フォルダが書き込み不可）では、クリアせず中止のダイアログが出る
6. サブフォルダ内のファイルのIDは消えない
