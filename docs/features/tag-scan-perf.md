# タグ自動抽出の高速化（zip の読み方）

「現フォルダ内タグ情報取得」（タグ自動抽出）の走査が、**HDDの初回（OSのキャッシュが冷たい状態）でとても遅かった**のを速くした。
718件・計20GBのフォルダで **131秒 → 13秒（約10倍）**。結果（取れるタグ・詳細・ページ数）は変えていない。

## 1. 原因（実測）

走査のほぼ全部が、zip を開く `ZipArchive::new`（zip クレート 2.4.2）の中にあった。

| 段階（冷たい状態・718件） | 変更前 |
|---|---|
| zip を開く（`zip_parse`） | 116.6秒（89%） |
| 先頭のマジック判定（形式の判別） | 8.6秒（6%） |
| 末尾の生read（参考） | 6.1秒 |
| 名前の分類・info.txt等の本体読み・DB・候補生成・確認窓 | 合計で約0.3秒 |

zip クレートは開く時に、**全エントリのローカルヘッダを1件ずつ読みに行く**（エントリの位置へシーク→読み→中央ディレクトリへ戻る、を全件）。
エントリ数の中央値は48、最大648。HDDではこのランダムシークが1件あたり約180msになる。
OSのキャッシュが温かいと同じ処理が0.13秒で終わるので、**純粋にディスクのシーク待ち**だった。
info.txt 等が欲しいだけなら、末尾の中央ディレクトリ（名前・方式・サイズ・位置の一覧。最大55KB）だけで足りる。

## 2. 仕組み

`read_zip_bundle`（[meta.rs](../../src/fs/archive/meta.rs)）が、まず**近道**で読み、判断できなければ**従来の経路**（zip クレート）に戻す。
結果は同じ。両方の経路が、名前の分類（`plan_entries`）と組み立て（`assemble_bundle`）を共通の関数で行う。違うのは、一覧の取り方と、本体の読み方だけ。

### 近道（[zip_cd.rs](../../src/fs/archive/zip_cd.rs)）

1. 末尾128KBを**1回**読む。EOCD（終端レコード）を後ろから探して解析する。
2. 中央ディレクトリが末尾の読みに収まっていれば、そのまま解析する。収まらなければ、足りない分を含めて1回だけ読み直す。
3. 一覧（名前・フラグ・方式・CRC・サイズ・ローカルヘッダの位置）ができる。**ローカルヘッダは読まない**。
4. 読む対象（info.txt・ComicInfo.xml・meta.json・付属テキスト）のエントリだけ、ローカルヘッダ（30バイト＋名前＋拡張）とデータを読む。stored と deflate を展開する。読む量の上限は従来と同じ。
5. 名前の分類は、拡張子・`/`・`\`・`info.txt` との一致だけを見るので、**ASCII の部分だけ**で足りる（`zip_cd::ascii_view`）。文字コードは解釈しない。本文のファイル名（付属テキストの表示名）は従来と同じ `decode_zip_name`。

### 従来の経路に戻る条件

近道が少しでも判断に迷ったら、zip 全体を従来の経路で読み直す（結果を変えないため）。

- ZIP64（件数・サイズ・位置が上限値）、複数ディスク
- 先頭に余分なデータがある（自己展開形式など）、中央ディレクトリの位置が EOCD の記録と食い違う、件数や大きさの不整合、中央ディレクトリが64MB超
- 読む対象のエントリが、暗号化されている・stored / deflate 以外（zstd・bzip2・lzma・AES など）
- 読む対象のエントリの CRC が合わない・読み取りエラー（従来は「読めなかった」扱い。戻して従来の挙動に揃える）
- 名前を差し替える拡張（Info-ZIP の Unicode パス `0x7075`）がある、または拡張領域が読み取れない（zip クレートは名前を差し替えるため）
- 読む対象でないエントリ（画像など）の圧縮方式は、何でも近道で答える（本体を読まないので）

### 先頭のマジック判定の省略

拡張子が `.zip` / `.cbz`（大文字小文字は区別しない）なら、`read_bundle_timed` は先頭を読むマジック判定を省き、近道を先に試す。
近道が**構造として整合して読めたときだけ**答えるので、中身が別形式の偽装（`.cbz` に 7z・tar など）には答えず、従来どおりマジック判定へ進む。
他の拡張子は従来どおりマジック判定を通す。

走査の中の `detail_supported(path)`（中身は `detect_format`＝先頭読み）は、zip として読めなかったときだけ判定する（[tag_scan.rs](../../src/view_explorer/tag_scan.rs)）。
引数として先に評価すると、読めた場合は使われない先頭読みが、毎回走ってしまう（実際にこれで約2秒を無駄にしていた）。

## 3. 結果（冷たい状態・718件・HDD）

| | 開始時 | 近道のみ | 近道＋マジック省略 |
|---|---|---|---|
| 走査 | 131.4秒 | 15.2秒 | **13.2秒** |
| 1件あたり（平均 / p99） | 183ms / 1019ms | 21ms / 42ms | 18ms / 67ms |

残り（`zip_parse` 10.2秒・`entry_read` 2.8秒）は、末尾の1回読みと、先頭側にあるエントリの先頭読み。**1件あたり1〜2シーク**で、HDDの物理的な床。

## 4. 既知の差

- 対象外のエントリ（画像など）のローカルヘッダが壊れた zip は、従来は「zip 全体が開けない（対象外）」、近道では「開けて、取れる分を取る」。近道のほうが寛容。
- 先頭のローカルヘッダが壊れていて、中央ディレクトリは整合している zip を `.zip` / `.cbz` の名前で置いた場合も、同じく読める（マジック判定が「zip ではない」と答えうるケース）。

## 5. 計測ログの見方（開発用）

設定の「perfログ」をONにして起動すると、タグ自動抽出のたびに、標準エラーに `[perf/tag-scan]` が1回出る（[tag_scan_perf.rs](../../src/view_explorer/tag_scan_perf.rs)）。OFFでは何も出ない。

- 1行目: 件数・走査の時間・候補生成の時間
- 段階別の合計（全体に対する割合）: `stat`（stat）・`magic`（形式判定の先頭読み）・`file_open`・`zip_parse`（近道では末尾の読みと中央ディレクトリの解析）・`name_list`・`entry_read`（info.txt 等の本体）・`zip_other`・`db`・`計測外`
  - **`計測外` が大きいときは、計測の外に重い処理が隠れている**（上の `detail_supported` の件はこれで見つかった）
  - `tail_raw` は従来の経路でだけ測る（perfログON時に末尾を生で1回読んで時間を分ける）。近道では常に0
- 1件あたりの時間（平均・p50・p90・p99・最大）、zip のサイズ分布、末尾（中央ディレクトリ〜）の大きさ、エントリ数
- 読んだエントリの位置: 先頭64KB以内／中央ディレクトリの手前64KB以内／それ以外（「中間にある」）。今回の実測は 先頭304・末尾413・中間0・無し1
- 確認窓を開くUIスレッドの時間

冷たい状態は、`sync; echo 3 | sudo tee /proc/sys/vm/drop_caches` で作れる（要sudo。ユーザーが実行する）。直後の再実行は温かい状態になる。

## 6. 検討して採らなかった案

- **RAMDISK へ全体を読み込む**: 読む量が約20GBになり、かえって遅い。必要なのは末尾の数十KBだけ
- **並列読み（スレッド数をプローブで自動決定）**: HDDで効くかが不確実。取り下げ
- **物理順に並べて処理**: 同上。取り下げ
- **候補生成・照合の高速化**: 0.12秒で、ボトルネックではない

## 7. 範囲の外（別件）

ビューアーで本を開くとき（`list_images_zip_with_progress`）やメモリ見積もり（`estimate_archive_memory_zip`）も、同じ `ZipArchive::new` を使うので、冷たいHDDでは同じ全エントリのシークを払っているはず（200ページで約0.7秒、650エントリで約2秒と推定）。
画像1枚ずつの読みまで `ZipArchive` に依存していて、直すには読み込みの経路全体を自前にする必要がある。影響範囲が大きいので、この件には含めていない。

## 8. 実装

- [zip_cd.rs](../../src/fs/archive/zip_cd.rs): 中央ディレクトリの解析（`read_central_dir`）、エントリ本体の読み（`read_entry_limited`、CRC検査つき）。テスト7件（zip クレートの見方との一致、追加読みの経路、ローカルヘッダを読まない証拠、異常系の戻し）。
- [meta.rs](../../src/fs/archive/meta.rs): `read_zip_bundle_timed`（近道→従来の順）、`read_bundle_timed`（マジック省略）、`plan_entries`・`assemble_bundle`（新旧共通）。等価テスト（`fast_path_*`・`zip_extension_*`）。
- [tag_scan.rs](../../src/view_explorer/tag_scan.rs)・[tag_scan_perf.rs](../../src/view_explorer/tag_scan_perf.rs): 走査と計測。

等価テストは、近道と従来の経路で結果が完全に一致することを確かめる。通常の zip（info.txt・ComicInfo・meta.json・付属テキスト4件上限・サブフォルダ・大文字小文字・`\` 区切り・コメント・空 zip・同名複数）、
1500エントリ＋末尾の info.txt、上限を超える巨大な本文（stored・deflate）、Shift-JIS名（UTF-8フラグなし）。近道が戻す側は、暗号化・zstd・bzip2・CRC破損・先頭ゴミ・非zip・切れた zip・Unicode パス拡張。

## 手動テスト手順

1. 冷たいHDDのフォルダ（数百件）で、perfログONのまま「自動タグ抽出」を実行すると、`scan_wall` が以前（約130秒）より大きく短くなる（目安: 100件あたり約2秒）。`計測外` の割合が0付近。
2. 同じフォルダを続けてもう一度実行すると、1秒未満で終わる（キャッシュが温かい）。
3. 取れるタグ・確認窓の内容・リストの「詳細」列・ページ数列が、変更前と同じになる（info.txt のあるもの・ComicInfo/meta.json のあるもの・どちらも無いもの）。
4. 暗号化（パスワード付き）の zip、zstd 等の圧縮の zip が混ざっていても、走査が止まらず、従来どおり「info.txt 無し」または取れる分だけ取れる。
5. 拡張子だけ `.cbz` で中身が 7z・テキストのファイルは、これまでと同じく対象外（N/A）になる。
6. Shift-JIS名のzip（日本語のフォルダ名の中に info.txt）で、info.txt が拾える。
7. 7z・tar・フォルダが混ざったフォルダでも、それらが対象外（N/A）のまま、zip だけ速くなる。
8. perfログをOFFにすると、標準エラーに `[perf/tag-scan]` が出ない。
