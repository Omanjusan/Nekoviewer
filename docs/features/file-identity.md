# ファイルID（フィンガープリント）管理

ファイルを「パス」ではなく「内容」で見分け、移動・リネーム後も評価・しおり・見開き・ソート・登録サムネ・タグ・
お気に入り・サムネを引き継ぐ仕組み。以前はこれらの記録が全て `ディレクトリ + ファイル名` をキーにしていたため、
ファイルを動かすと記録が失われていた。

関連文書: [解決UIのレイアウト仕様](fingerprint-resolution-ui.md) / [開発用DBバックアップ](../dev-db-backup.md) /
[統合テスト手順書](file-identity-test-checklist.md) / [キャッシュ設計（サムネ）](../cache-design.md)

## 1. 考え方

- **同一性は内部ID**。ファイルごとに1つ振る（`file_id_v1`）。**FP（フィンガープリント）は照合キー**で、
  「このパスのファイルは、記録済みのどのIDと同じ内容か」を調べるために使う。同じ内容のコピーはFPが同じでもIDは別。
- 記録の置き場は `nekoviewer_spread.redb`（キャッシュ整理の対象外）。ID層のテーブルは、最初に使う時まで作らない
  （旧パス仕様のDBを、起動や読み取りだけで変えない）。最初のID作成で、FP仕様のマーカー（`identity_meta_v1`）が立つ。
- 旧（パスキー）のテーブル（以下「旧v1」）の行は**消さない**。ID化前の記録を、移動・リネーム後でも旧パスキー経由で
  引けるようにするため。

## 2. FP

- 内容: サイズ＋サンプルのSHA-256（先頭16バイト）。256KB以下は全体、それ以上は先頭・25%・50%・75%・末尾の各32KB
  （ZIPの中央ディレクトリは末尾窓に入る）。0バイトのファイルはFPなし（パスだけで識別）。
- `open → read → close` で完結し、ハンドルを保持しない。
- 既知の限界: サイズが同じで、窓の外だけが違うファイルは同じFPになる（無圧縮画像など。zip/7z/rar/jpg/pngでは実質起きない）。
- 書き込み中のファイル（mtimeが3秒以内、または読む前後でサイズ・mtimeが変わった）はFPを取らず後回しにする。

## 3. 解決のルール（`file_identity.rs`）

新しいパス（パス索引にまだ無い）が現れたとき、FPの一致するIDを調べる。**消えている**＝元のパスにファイルが無い
（ボリュームはオンライン）、**現存**＝元のパスにまだある、**オフライン**＝ボリュームが見えない（候補にしない）。

| 状況 | 結果 |
| --- | --- |
| パスが記録済み | 同じID。FPが違えば内容更新（IDは同じ。しおりだけFP不一致で無効になる） |
| 消えている候補が1つ、または全員同じデータ（誰も持たなければ mtime一致>名前一致>古い順） | **移動**。同じIDがそのパスへ移る（お気に入りを含む全データが付く） |
| 消えている候補が複数でデータが食い違う | 割り当てを保留し、新IDは空のまま作る。**未解決（移動元の選択）** |
| 消えている候補が無く、現存の候補（データあり）が1つ、または全員同じデータ | **複製**（Copied）。元のデータを1回だけ複製する（以後は独立） |
| 現存の候補が複数でデータが食い違う | 新IDは空のまま作る。**未解決（引き継ぎ元の選択）** |
| 新側のパスに旧v1データがある／候補にデータが無い／候補がオフラインだけ | 通常の新規（複製しない） |

- 「データの食い違い」は、`spread_state::data_signature`（評価★・有効なしおり・見開き・ソート・登録サムネ・タグ。
  訪問回数は含めない）の一致で判定する。**移動の判定はお気に入りも署名に含め、コピーの判定は含めない。**
- 複製するもの: ★（訪問回数・最終訪問は0）・しおり（FPつき）・見開き・ソート・登録サムネ・タグ・サムネ。
  **お気に入りは複製しない**（現UIでは「どの場所のお気に入りか」を区別できず、重複を後から足すと破綻するため）。
- 内容更新で、ユーザーデータが空のIDが同FPの孤児IDを見つけたとき（別FS間の移動の途中を拾った場合）は、
  空のIDを消して孤児を新パスへ移す（候補が曖昧なら統合せず、未解決にする）。
- IDには、直近3件の旧パス（`history`）と、作成時のパス（`origin_key`、不変）、ボリューム（マウントルートのパス。
  オフライン判定用）を持たせる。

## 4. テーブル（`nekoviewer_spread.redb`）

| テーブル | キー → 値 | 役割 |
| --- | --- | --- |
| `file_id_v1` | ID → レコード | パス・サイズ・mtime・FP・ボリューム・状態・最終確認・履歴 |
| `file_path_index_v1` | パスキー → ID | 高速経路（stat一致ならFPを読まない） |
| `file_fp_index_v1`（multimap） | FP → ID | 移動・コピー候補の検索 |
| `identity_counters_v1` | 名前 → u64 | ID・未解決記録IDの採番 |
| `identity_meta_v1` | `identity_enabled` → 1 | FP仕様のマーカー（旧パス仕様DBと区別。開発用バックアップのガード） |
| `file_settings_v2` | ID → レコード | 見開き・ソート・登録サムネ・タグ・お気に入り所属（下記） |
| `archive_rating_v2` | ID → (★, 訪問回数, 最終訪問) | 評価・訪問 |
| `bookmark_state_v2` | ID → (有効, 位置, 更新日時, mtime, FP) | しおり（有効判定はFP一致、不明ならmtime） |
| `identity_pending_v1` | 記録ID → (種別, 対象ID, 候補ID群, 検出日時) | 未解決（重複・曖昧） |

- パスキーは従来どおり `{正規化したディレクトリ}\0{ファイル名}`（`spread_state::make_key`）。
- `file_settings_v2` のフィールドは3状態: **未移行**（旧v1を引く）／**値あり**／**解除済み**（旧v1が残っても復活させない）。
  書き込み時に、そのファイルの未移行フィールドを旧v1から一括で引き継ぐ（`file_settings::modify`）。
- 読み取りは、IDが解決済みならv2（未移行なら旧パスキー `legacy_keys` で旧v1）、未解決・実体なしなら旧v1のパスキー。
  実体が無くてIDを作れないファイルへの書き込みは、従来どおり旧v1へ書く。
- **GC（消えたファイルの行の削除）は、評価・しおり・見開き・ソート・お気に入りの全てで廃止した。**
  旧v1の行は移行の橋渡しとして残す。

## 5. 解決ワーカーとUI（`view_explorer/identity_worker.rs`）

- フォルダ表示（スキャンとソートの直後）に、一覧を表示順にワーカーへ投入する。stat一致なら何もせず、不一致なら観測→解決。
  DBロックは1件ごとに「読み取り→（ロック外で）存在確認→書き込み」の3段階で短く握る（競合は最大3回やり直す）。
- 新しいスキャンで世代が進み、古いバッチは次のファイルの前で打ち切る。書き込み中のファイルは4秒おき最大3回再試行する。
- ID記録も旧データも無いファイル（新規・移動直後）のサムネには「ファイル検証中」を重ね、**解決が済むまでサムネ生成を始めない**
  （サムネの引っ越しが空振りしないため）。結果は10件ずつ通知し、移動・複製・統合があった時は★・評価帯・見開き等の一覧を引き直す。
  完了時に、付き替わりがあれば並びを1回だけ作り直す。
- 処理が2秒を過ぎても終わらないときだけ、「ファイルを検証しています… n / 総数」のトースト（`set_sticky_toast`）を出す。
- 起動の約5秒後から、旧v1にユーザーデータがあるのにIDが無いレコードを、ジョブが無い間に1件ずつID化する（バックフィル）。
  未訪問フォルダのファイルも、アップグレード後すぐ移動追従の対象にするため。実体が無いもの（移動済み）は救えない。
- ユーザー操作（評価の書き込み・ビューアを開く等）は、未解決のファイルのIDを同期で解決する（`ensure_record`）。

## 6. サムネ（`neko_dir.rs`）

- ディレクトリ別の `cache.redb`（ファイル名キー）は維持する。**キーのID化はしていない。**
- 移動・リネーム・複製と分かった時点で、元のDBの生成済み（Current）サムネの行を新しい名前（別フォルダのDB可）へコピーする
  （`take_thumbnail_rows` / `put_thumbnail_rows`）。移動先で生成中・生成済みなら上書きしない。サムネ本体のmtimeは持ち越すので、
  別FSへのコピーなどでmtimeが変わった場合は、通常のmtime突合で再生成される。元の行は消さない。
- `sync_thumbnail_records` は、消えたファイルのサムネ行を**消さない**（検索用の索引と非画像マーカーだけ掃除する）。
  残った行の掃除は、別ブランチ予定のキャッシュ整理（未確認のまま一定期間で削除）の役割。

## 7. 未解決と解決（`identity_pending.rs` / `identity_resolve.rs`）

- 自動では決められない項目を未解決として記録する。種別は、引き継ぎ元の選択（`CopySource`）、移動元の選択（`MoveTarget`）、
  お気に入りの引き継ぎ（`FavoriteHandover`）。同じ（種別, 対象）は1件にまとめ、新しく増えた時だけ通知トーストを出す。
- 状況が変わって意味を失った記録（対象に記録が付いた、候補が消えた・戻ってきた等）は、解決の完了時と一覧を開く時に自動で除く
  （`prune`）。日数による削除でIDが消えた場合も、候補が尽きた項目はここで消える。
- お気に入りの引き継ぎは、実体の無いお気に入りに同内容の現存ファイルがある時（コピー→元を削除の取りこぼし）に、
  一覧を開く時に検出する。移動だけなら、そのファイルを開いた時にIDごと自動で追従する。
- 解決は `identity_resolve::apply`。引き継ぎ元＝データの複製、移動元＝選んだ孤児IDを新パスへ移す（空の新IDは消える。
  新ファイルにデータが付いていたら適用しない）、お気に入り＝所属を移し先へ移す（既存の所属と合流）。
  適用前に前提（記録・候補・IDの存在、対象が空か）を確かめ、崩れていれば何もせずエラーを返す。
- UIは [fingerprint-resolution-ui.md](fingerprint-resolution-ui.md)。ボタン「DB内の重複の解決（n）」は未解決が無いとグレー。

## 8. 設定

- 「未確認IDの保持日数」: 設定→その他。1〜120日、既定60日（`app_unconfirmed_retention_days`）。解決UIの
  「削除まで残り○日」の元。**日数による削除そのものは未実装**（キャッシュ整理ブランチで行う）。

## 9. 既知の限界・割り切り

- 移行前に動かされたファイルの旧データは救えない（FPが残っていないため）。バックフィルは、アップグレード後に走った分だけ。
- 「名前の入れ替え」（2つのファイルの名前を交換）は、パスが優先されるため復元できない。
- 消えた旧v1の行・消えたファイルのサムネ行は残り続ける（掃除はキャッシュ整理の役割）。
- ダウングレードは非保証（新版が書いたv2は旧版から見えない。旧版が書いた旧v1は再アップグレード時に再コピーしない）。
- 数十万ファイル規模では、お気に入りの横断一覧（IDレコードの全件走査）に時間がかかりうる。
